# CDP 干净浏览器标准方案（2026-03-16）

## 结论

SO101 项目的默认浏览器演示方案统一为：

- 干净浏览器 CDP
- 可见窗口
- 独立 profile
- 固定调试端口 `9223`
- 不接管用户日常 Chrome

这套方案适用于：

1. ROS2 仿真联调
2. 前端演示与答辩
3. Gazebo / RViz / frontend 同屏展示
4. 可重复自动化与截图取证

## 不采用的默认方案

### 1. 不默认采用用户级别 Chrome CDP

原因：

- 会污染用户日常 Chrome 环境
- 容易碰到已有标签页、扩展、登录态干扰
- 在 WSL + ROS2 + Gazebo + RViz 的演示场景下，稳定性不如干净 profile

### 2. 不默认采用临时 Playwright launch 作为长期标准

原因：

- 虽然能跑通，但它更像一次性自动化浏览器
- 生命周期和可管理性不如固定 CDP 方案
- 不适合作为长期演示标准

## 选择优先级

1. Windows 原生 Chrome / Edge + 独立 profile + CDP
2. Linux 原生 Chrome / Edge / Chromium + 独立 profile + CDP
3. Playwright bundled Chromium（仅兜底，不作为默认标准）

## 标准参数

- Windows 原生浏览器 profile：`C:\Users\11614\AppData\Local\so101-mes\cdp-browser-profile`
- Linux / Playwright fallback profile：`/home/muqiao/dev/ros2/workspaces/so101_ws/.vscode/.runtime/cdp-browser-profile`
- 浏览器日志：`/home/muqiao/dev/ros2/workspaces/so101_ws/.vscode/.runtime/gui_browser.log`
- 浏览器 pid：`/home/muqiao/dev/ros2/workspaces/so101_ws/.vscode/.runtime/gui_browser.pid`
- CDP 调试地址：`http://127.0.0.1:9223`
- 默认打开页面：`http://127.0.0.1:5173`

## WSL 约束

- 在 WSL 中直接让 Windows Chrome 读 `\\wsl.localhost\...` 目录，会出现 profile 锁和沙箱报错
- 因此默认 profile 已迁移到 Windows `LocalAppData`
- 这不是“用户级别浏览器”，仍然是独立 profile，不接管你的日常 Chrome

## 启动入口

### 后端 API

- `POST /api/system/open-browser`
- `POST /api/system/stop-browser`
- `GET /api/system/status`

### 本地脚本

- `tools/browser/start_clean_cdp_browser.sh`

## 当前前端能力

前端 `System Control` 面板已经支持：

1. 打开干净浏览器
2. 关闭干净浏览器
3. 查看浏览器状态
4. 查看浏览器 pid / log / debugUrl

## 推荐使用方式

### 日常联调 / 答辩演示

1. 启动 backend
2. 启动 frontend
3. 前端点 `打开干净浏览器`
4. 前端点 `启动 Gazebo 仿真`
5. 前端点 `打开 RViz`
6. 前端点 `连接 WebSocket`
7. 创建工单并直接下发

### 需要接管页面时

如果后续需要自动化控制页面，应优先：

1. 连接 `http://127.0.0.1:9223`
2. 操作这套干净 profile 的浏览器
3. 不直接接管用户日常 Chrome

## 例外

只有在以下场景才考虑切换到用户级别 Chrome CDP：

1. 明确要求必须操作用户当前 Chrome
2. 页面依赖用户已有登录态
3. 需要复用用户已安装扩展

除此之外，项目默认仍保持干净浏览器 CDP。
