# HWP-005 WSL2 COM4 主臂转发与环境策略

## 目标

在只考虑主臂、且 Windows 侧已能完成校准的前提下，把 `COM4` 对应的主臂串口稳定转进 WSL2，并明确本轮的软件环境策略。

本轮只解决三件事：

1. `usbipd-win 5.3` 下如何恢复被残留共享卡住的 `COM4`
2. 如何把主臂 CH340 串口重新 attach 到 `Ubuntu-22.04`
3. 当前这条链路要不要上 conda

## 本机已确认事实

- `usbipd-win` 版本：`5.3.0`
- `COM4` 设备：`USB-SERIAL CH340 (COM4)`
- 当前识别：
  - `BUSID = 2-2`
  - `VID:PID = 1A86:7523`
  - 当前 `usbipd list` 状态为 `Shared`
- `Ubuntu-22.04` 当前是目标 WSL 发行版
- WSL 当前系统 Python：
  - `python3 = 3.10.12`
  - `pyserial = 3.5`

结论：

- 这条主臂串口链路当前不需要为了“串口接入”单独引入 conda。
- 先用系统 Python 即可。

## 环境策略

### 1. 本轮不引入 conda

原因：

- 当前真机骨架脚本都基于 ROS2 Humble + 系统 Python 运行。
- `pyserial` 已存在于系统环境。
- conda 与 ROS2 混用时，最容易引入：
  - `PYTHONPATH` 覆盖
  - `rclpy` / `numpy` / `yaml` 版本冲突
  - launch 环境与 shell 环境不一致

因此本轮原则是：

- `ROS2 + 真机桥接 + 串口 smoke` 全部走系统 Python
- 只有在后续真实驱动目录明确要求独立依赖且与 ROS2 冲突时，才单独给它一个隔离 `venv`
- 不优先选 conda

### 2. 如果未来必须隔离

优先级：

1. 系统 Python
2. 项目内 `python -m venv`
3. 最后才考虑 conda

## 已新增脚本

### Windows 侧恢复/attach

- `tools/hardware/windows_usbipd_recover_attach.ps1`

作用：

- 先 `unbind --busid 2-2`
- 可选 `Restart-Service usbipd`
- 再 `bind --busid 2-2`
- 最后 `attach --wsl Ubuntu-22.04 --busid 2-2 --auto-attach`

### WSL 侧包装入口

- `tools/hardware/attach_main_arm_com4_to_wsl.sh`

作用：

- 从 WSL 直接调用 Windows PowerShell 脚本
- 默认使用：
  - `BUSID=2-2`
  - `HARDWARE_ID=1A86:7523`
  - `WSL_DISTRO_NAME=Ubuntu-22.04`
- attach 成功后等待：
  - `/dev/ttyUSB*`
  - `/dev/ttyACM*`

### 主臂串口状态导出器

- `tools/hardware/export_main_arm_serial_status.py`

作用：

- 用最保守方式把“主臂串口是否已进 WSL”导出成现有真机 contract 源 JSON
- 默认：
  - 只检查串口是否存在且可打开
  - `allowExecute=false`
  - `powerState=未上电`
  - 不尝试放行动作

### Command Target Config 示例

- `tools/hardware/real_hardware_adapter_target.main_arm_serial.command.example.json`

作用：

- 让 `HWP-004` 的 smoke harness 能直接用主臂串口状态导出器接入

### 自动刷新与校准同步

- `tools/hardware/refresh_main_arm_runtime_state.sh`
  - 启动后立即把主臂串口状态写回 runtime contract
  - 默认把主臂控制板视为 `已上电`
  - 默认保持 `allowExecute=false`
- `tools/hardware/watch_main_arm_runtime_state.sh`
  - 以后台 watcher 方式持续刷新 runtime contract
  - 解决 backend 15 秒 freshness 窗口导致的 `STATUS_TIMEOUT`
- `tools/hardware/sync_real_hardware_calibration.py`
  - 校验并写入 `.vscode/.runtime/real_hardware_calibration.json`
  - 只有提供真实 calibration profile 后，backend 才会把“已校准/已回中”反映到 `/api/system/status`

## 推荐操作顺序

### 1. 先做 dry-run

```bash
cd /home/muqiao/dev/ros2/workspaces/so101_ws
bash tools/hardware/attach_main_arm_com4_to_wsl.sh --what-if
```

### 2. 如果 COM4 又进入“Shared 但 Windows 不认”状态

必须在“管理员权限”的 Windows Terminal / PowerShell 上下文执行。

也就是说：

- 如果你从 WSL 里跑脚本，这个 WSL 会话本身最好是从“管理员 Windows Terminal”拉起来的
- 普通权限的 WSL shell 无法执行 `usbipd unbind` 和 `Restart-Service usbipd`

然后执行：

```bash
cd /home/muqiao/dev/ros2/workspaces/so101_ws
bash tools/hardware/attach_main_arm_com4_to_wsl.sh --restart-service
```

### 3. attach 成功后导出主臂端口

脚本会输出类似：

```bash
export SO101_MAIN_ARM_PORT=/dev/ttyUSB0
```

### 4. 用主臂串口状态跑 smoke

```bash
cd /home/muqiao/dev/ros2/workspaces/so101_ws
export SO101_WS_ROOT=/home/muqiao/dev/ros2/workspaces/so101_ws
export SO101_MAIN_ARM_PORT=/dev/ttyUSB0
bash tools/hardware/run_real_hardware_target_smoke.sh \
  tools/hardware/real_hardware_adapter_target.main_arm_serial.command.example.json
```

### 5. 查看运行时 contract

```bash
cat .vscode/.runtime/real_hardware_status.json
cat .vscode/.runtime/real_hardware_command_gate.json
cat .vscode/.runtime/real_hardware_adapter_smoke_report.json
```

### 6. 真机最小 bringup 现在会自动刷新主臂在线态

```bash
cd /home/muqiao/dev/ros2/workspaces/so101_ws
export SO101_MAIN_ARM_PORT=/dev/ttyUSB0
bash tools/hardware/start_real_min_bringup.sh
```

如果你已经有真实校准文件，再额外给：

```bash
export SO101_MAIN_ARM_CALIBRATION_PROFILE=/ABS/PATH/TO/real_hardware_calibration.json
```

这样启动后：

- 主臂在线态会自动刷新
- watcher 会持续保活状态新鲜度
- calibration file 会同步到 runtime

## 风险边界

- 当前脚本只解决“主臂串口进入 WSL + 状态桥接 smoke”
- 还没有实现：
  - 真正的主臂协议读状态
  - 真实上电判定
  - 真实急停判定
  - 真机动作控制

所以即使串口接通：

- 仍然必须保持 `gate.enabled=false`
- 仍然必须保持 `allowExecute=false`
- 仍然只能算 `HWP-002/HWP-004` 的接入推进，不能算 `HWS-001/CAL-001` 完成
